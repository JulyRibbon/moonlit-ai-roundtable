## 三、写 Bridge 必须遵守的 7 条（每条都有实测依据）

1. **collector 先就位再投递**：`turn/start` 可能比 `prompt` 的 HTTP 响应更早到（43.191 vs 43.195）。
2. **关联只能按「该会话下一个新 turn」**：`prompt` 只回 `{accepted:true}`，**没有 turn id**。
3. **席位会话专席专用**：机主若在 GUI 手动聊同一会话，那些 turn 也会出现在我们的订阅里 → 必须能区分 `foreign`，不能进房间字幕。
4. **快照只喂账本**：`session/snapshot` 含历史 `turn/end`，重放会导致重复发布。
5. **断线恢复按「有 start 无 end」重建 collector**：否则那一轮回复被静默丢弃（token 却照付）。
6. **`aborted` 的部分正文不进字幕**，只进 attempts（实测取消前已生成 73 行）。
7. **去重键是 `(sessionId, turn)`**，不是文本、不是时间；同一句话两轮都说是合法的。
8. **第一条 turn 的 `turn/start` 可能落在开场快照里**（复现过）：follow 之后立刻投递时，
   live 通道只来了 `assistant/message`，`turn/start` 在快照 `records` 里。
   不在快照里重建「有 start 无 end」的回合，这一轮正文就丢了。探针已按此修正（7/7 通过）。

## 四、探测到的接口清单

```
sessions.list({})                                  → {items:[{sessionId,title,running,blank,cwd,projections:{values:{agentPreset,modelSelection,tokenUsage,inbox,title}}}]}
sessions.create({workspaceId?, agentPreset})        → {sessionId}
workspace.create({path})                            → 目录必须已存在，否则 workspace/invalid-path（realpath 失败）
workspace.archiveSession({sessionId})               → OK
events.mux({}) + events.follow(sessionId)           → session/snapshot + session/event
sessions.prompt({sessionId, mode:'queue', content}) → {accepted:true}
session/projections({sessionId})                    → values.inbox = {"next-turn":[], "next-step":[]}
session/updateQueue({sessionId, itemId, action:{kind:'remove'}})  ← 清队列用（桥接已验证，本次未单独跑）
session/cancel({sessionId})                         → {ok:true}
```

> 注意：`session/projections` 的 payload 在传输层会被包成 `{args:{request:{sessionId}}}`；
> `session/list` 用的是 `_request` 而不是 `request`。直接用基类门面 `api.sessions.*` 就不用管这层。

## 五、语音：结论是「没有」

- 事件类型全表（实测）：`agent/inbox/spliced`、`turn/start`、`step/start`、`system/message`、`user/message`、
  `request/header`、`request/context`、`session/title`、`session/title-llm-request`、
  `session-log-deepseek/delivery-accepted`、`assistant/message`、`step/end`、`turn/end`。
  **没有任何 speech / voice / audio 帧。**
- DSH 设置命名空间里只有 `speech-to-text`（语音输入），没有 TTS / 朗读 / 播报项。
- 因此：外部投递触发的回答，DSH **不会**自动朗读。DSH 席位 `voiceMode = none`，UI 不显示 speaking 状态。
- 若机主在 GUI 前亲耳听到朗读，再单独记一条反例——**以耳朵为准，不以我的结论为准**。

## 六、权限直通：M0 必须定下来的事

实测当前会话 `permissions.currentValue = "danger-full-access"`，`cwd = C:\DSHW`。
房间把「其他 AI 成员说的话」投进这样一个会话，等于**把本机执行权交给了一个会被同伴影响的代理**。

三条路（需要机主选一条，我不替你选）：

| 方案 | 人格 | 风险 | 工作量 |
| --- | --- | --- | --- |
| A. 保持 `cordis`/`standard` 原样 | ✅ 完全原生 | 跨模型指使可执行本地命令 | 0 |
| B. 换 `minimal` 等受限 preset | ❌ 人格被换 | 低 | 0 |
| C. 新写「房间专用 preset」：同一份 AGENTS.md 人格 + restrict 掉本地工具 | ✅ 基本保持 | 低 | +0.5 天 |

我的倾向：**探测阶段用 A（已经跑完），正式接入前选 C**；如果机主愿意承担风险选 A，我也照办，但会在桥接里加「消息来源标注 + 可疑指令告警日志」。
